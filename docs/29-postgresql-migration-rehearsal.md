# PostgreSQL migration and recovery rehearsal

Status: S09/AT26 partial, local synthetic integration evidence only. Production remains on its existing SQLite/Fly release. No managed PostgreSQL service was purchased, configured or written to.

## Implemented paths

- `prisma/schema.prisma` and `prisma/migrations` remain the canonical SQLite track.
- `prisma/postgresql/schema.prisma` and `prisma/postgresql/migrations` are a separate provider-specific track. PostgreSQL SQL is generated by Prisma against PostgreSQL datamodels, never copied from SQLite migration SQL. The source-version record ties it to the current canonical schema and requires production review.
- `scripts/prepare-postgres-track.ts` generates a new append-only PostgreSQL migration when the canonical schema changes. Existing migration files are not rewritten. `--check` fails if the track is absent/stale. Review the generated SQL before accepting it; automatic generation is not approval to drop or change production data.
- `scripts/lib/postgres-transfer.ts` takes a consistent private SQLite snapshot, validates integrity/FKs, exports scalar records in 100-row batches, imports into an EMPTY PostgreSQL public schema in one transaction, validates deferred FKs, and compares row counts and canonical per-table SHA-256 hashes. A populated target is rejected; there is no overwrite, dual-write or cutover action.
- A restored SQLite source carrying `_PagneticRecoveryHold` is rejected unless its signed RELEASED hold, exact signed replay evidence and signed release audit all verify against the recovery key and bind to each other. A status string or older recovery cycle cannot authorize transfer.
- `scripts/rehearse-postgres.ts` owns a new temporary PostgreSQL cluster accessible only through a private Unix socket. It creates synthetic fixtures, generates a separate temporary Prisma client, uses the actual PostgreSQL migration track, transfers and checks data, registers/verifies that exact migration history with Prisma, exercises concurrent workers, and performs `pg_dump`/`pg_restore` into another new local database. It then stops and removes only its own temporary cluster/client directories. It does not accept a production database URL.

## Running the local checks

Use the project-pinned Node runtime and installed dependencies, plus local PostgreSQL16+ (`postgres`, `initdb`, `pg_ctl`, `psql`, `createdb`, `pg_dump`, `pg_restore`) and `sqlite3` on PATH.

```sh
node --import tsx scripts/prepare-postgres-track.ts
node --import tsx scripts/prepare-postgres-track.ts --check
node --import tsx --test tests/postgres-transfer.test.ts
node --import tsx scripts/rehearse-postgres.ts
```

Inspect generated migrations before accepting the track. The rehearsal writes `docs/audit-2026-09-05/postgres-rehearsal.json`, containing only schema/migration hashes, per-model counts/hashes, timing and assertion outcomes—not source rows, secrets or shopper records. Rerun after schema changes; a schema change during the run is explicitly flagged and causes a failing exit.

The first setup attempt exposed Prisma's package resolution requirement: a client generated from an arbitrary OS temporary schema could not resolve the installed `@prisma/client`. The rehearsal now uses a uniquely owned temporary code-generation directory under the project while keeping the database/socket in a private short OS path. It never replaces the application's default SQLite client.

## What the current fixture proves

The settled local run uses PostgreSQL16.15 and all69 current application tables, with populated records covering two tenants, Unicode and nullable fields, a Shopify numeric identity above JavaScript's safe integer range, approved content, unchanged legacy protocol/report hashes, a legacy session assignment, decimal legacy order/refund money, v2 order/line/refund decimal-string minor units above the32-bit range, privacy/recovery schema and authenticated recovery transfer authority. The evidence JSON records the exact schema and both migration histories.

Two independent PostgreSQL Prisma clients concurrently claim12 queued jobs. The combined claims are unique; wrong-tenant completion and repeated/stale completion are rejected. The rehearsal also exercises lifecycle cohort locking, financial finalization/writer interleaving, six conflicting product deployments plus exact replay, rotated privacy intake, artifact contention, suppression lookup and frozen-report behavior. It refuses a held recovery source and accepts the same source only after authenticated audited release. This is real local database contention, not a mocked repository test; it is not production-shaped traffic.

After transfer, Prisma's PostgreSQL migration history is adopted only for the SQL actually applied, `migrate deploy` finds no pending changes, and a database-to-datamodel diff is empty. A second import into the populated target is rejected with existing rows preserved. The isolated PostgreSQL dump/restore retains all modeled row hashes and validated constraints. Timings describe this small fixture only, never a customer-data-scale RPO/RTO or managed PITR guarantee.

## Data semantics and safeguards

- IDs and integer fields cross the CLI boundary as decimal text; no JSON-number conversion of BigInt. Int32 overflow fails rather than wrapping. New financial fields already use exact decimal strings and survive unchanged. Legacy Decimal fields are normalized without floating-point arithmetic; unsupported types/ranges fail explicitly. Migration does not repair precision already lost by historical storage.
- DateTime values normalize to UTC with millisecond precision, booleans normalize0/1 to true/false, strings and JSON-as-string fields retain their contents. PK ordering is explicit and uses binary/C collation for text. Composite keys are supported.
- The target must be empty. Data/DDL imports run transactionally, FKs are deferred only during import and returned to non-deferrable semantics after validation. No trigger disabling or superuser bypass is used by the transfer function. Normal failures suppress raw SQL stderr because it can contain source data; verbose diagnostics are limited to explicitly synthetic setup calls.
- Private snapshot/SQL files are removed on normal success/failure. A host crash still requires cleanup of its explicitly identified private temporary files under the approved encrypted-storage policy. Default remote PostgreSQL connections use certificate-verified TLS; the local rehearsal explicitly disables TLS only for its non-network Unix socket.
- Existing SQLite migration history is not inserted as PostgreSQL history. The exact source migration file hashes are retained as evidence; the new provider's applied migration records are distinct. A real source export must additionally archive its actual applied SQLite migration receipts and frozen release identity.
