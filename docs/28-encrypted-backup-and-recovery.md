# Pagnetic v2 encrypted backup and recovery

Status: S08 code-controlled implementation; real bucket, key escrow, monitoring and full application recovery drill are not verified. This runbook supersedes the previous plaintext `.sqlite` plus checksum workflow for new backups. Existing artifacts are not deleted or migrated automatically.

## Scope and readiness

One supervised SQLite writer/design partner only. The pilot target is RPO ≤24 hours and full incident RTO ≤4 hours. The production supervisor attempts a backup every six hours, leaving retry margin. Database integrity restoration is tested each successful run; this does not prove the time needed to provision a replacement machine, retrieve secrets, restore application access and replay work. Managed PostgreSQL/PITR remains the gate before multiple unattended partners/writers.

`pnpm check:production` no longer accepts any filename ending in `.sqlite`. It verifies the latest manifest's keyed authentication, ciphertext checksum and length, configured remote destination, readback/restore timestamps within 24 hours, and recorded integrity checks. An in-memory test adapter cannot pass this gate. An old successful backup does not mask staleness; a failed new run cannot replace the prior proof.

## Owner/operator configuration before deployment

1. Choose/approve an S3-compatible bucket independent of the application volume. Existing approved storage can be reused. No bucket, account, paid service, region choice or legal approval was created by this implementation.
2. Configure `BACKUP_S3_ENDPOINT` (HTTPS origin), `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET`, `BACKUP_S3_PREFIX`, `BACKUP_S3_ACCESS_KEY_ID`, and `BACKUP_S3_SECRET_ACCESS_KEY` in the secret manager. The dedicated writer needs object put/get and bounded list on this prefix (including the immutable `pagnetic-privacy-*` receipt objects), not deletion or public access. Scope list to the exact prefix and deny delete/overwrite where the provider supports conditional policy. Require private access and TLS; configure appropriate provider encryption, versioning and retention independently.
3. Generate a separate random 32-byte base64 `BACKUP_ENCRYPTION_KEY` through the approved secret-management process. Do not put it in chat, Git, logs, an artifact manifest or the same bucket. Do not reuse `FIELD_ENCRYPTION_KEY`. Escrow the backup key, database field key, required application secrets and their key/release history outside the Fly machine. Rotation sets the new active key and retains up to seven old base64 keys in `BACKUP_ENCRYPTION_PREVIOUS_KEYS`; do not remove one while a backup, receipt or signed recovery chain references it. New artifacts use only the active key. Manifest restore, receipt replay, audited release, startup and database transfer select and authenticate the exact retained historical key; missing, malformed or corrupt history fails closed.
4. Set `DATABASE_URL=file:/absolute/database.sqlite`, `BACKUP_DESTINATION=/data/backups` and a deployment-specific `APP_RELEASE`. Relative database URLs are deliberately rejected: Prisma and the SQLite CLI resolve them differently. Keep the local directory private; provision headroom for the snapshot, download and restore scratch copies as well as retained encrypted backups. Current uploads stream without loading the database into application memory, but are limited to 5 GiB and a two-minute timeout per remote operation.
5. Configure the approved data-retention schedule in the storage provider. Local encrypted cache retention now defaults to eight verified copies (`BACKUP_LOCAL_KEEP`, allowed range2–30). After a successful new backup, only authenticated obsolete artifact/manifest pairs for the configured destination can be removed, and only after re-downloading the retained latest copy. Unknown, linked, corrupt and old-key files remain untouched for operator review. A conservative free-space preflight protects the database, scratch and cache filesystems before snapshot creation; it is not a disk reservation or ongoing monitor. See `docs/38-backup-cache-retention-and-headroom.md`. Provider retention, disk monitoring and encrypted-host temporary storage remain operational gates requiring verification.
6. Run `scripts/backup-sqlite.sh` using the pinned Node runtime and installed project dependencies. It prints the artifact identifier/duration and local retention summary, never credentials. A retention failure exits nonzero but explicitly preserves the distinction that the new backup was verified. Check `latest-verified.json` and record its immutable manifest object name in the incident/release record. Export that identifier outside the machine so recovery does not depend on the lost volume.
7. Run `pnpm check:production` and arrange an external check for failed jobs, missing/future/stale backup evidence and disk pressure. Local stderr is not a delivered incident alert. No external monitoring delivery is certified by this code checkpoint.

## Artifact and failure behavior

- A consistent `VACUUM INTO` snapshot includes committed WAL rows. Integrity and foreign-key checks run before encryption. Source data is never copied directly while live.
- AES-256-GCM encrypts the snapshot with a random nonce. The manifest records ciphertext/plaintext SHA-256, schema digest, app release, timestamp, key identifier, nonce/tag and restore proof. HMAC-SHA-256 authenticates the canonical manifest with domain separation. It contains no key, token, shopper record or signed URL.
- The encrypted object is uploaded, downloaded again and authenticated/decrypted into a private temporary directory. Restored bytes and SQLite integrity are checked. Only then is the manifest published remotely and locally, after remote manifest readback. Latest-local proof is switched atomically.
- Temporary plaintext is removed on normal success/failure; host crash recovery must address abandoned private temporary directories under the provider's encrypted-disk policy. An interrupted job can leave remote orphan ciphertext, but cannot publish successful proof before restore. Failed partial runs do not delete user files or older successful backups.
- A manifest is specific to one key and object; changing the destination, timestamp, checksum or release invalidates authentication. Download/upload failures, corrupt data and wrong keys fail closed. A remote outage is not treated as a successful local backup.

## Recovery drill and real recovery

1. For a drill, use a disposable isolated host with the pinned runtime, matching application release, SQLite CLI and approved secret access. Disable outbound jobs, webhook delivery, billing and storefront serving. A drill must never replace the live database or mutate Shopify.
2. Retrieve the manifest object name from the external release/incident record or operator-controlled bucket listing. Select the matching escrowed key. The script uses configured object storage; it does not trust an arbitrary download URL.
3. Run `scripts/restore-sqlite.sh pagnetic-UUID.sqlite.enc.json /absolute/NEW-database.sqlite` with the actual recorded object name. It downloads the manifest and artifact, selects the matching retained key, checks keyed integrity, restores and validates in isolation, then exclusively creates both the destination and `/absolute/NEW-database.sqlite.verified-manifest.json`. The command prints that exact usable manifest path. An existing database or manifest causes failure; a manifest collision rolls back only the database created by that invocation. There is no force-overwrite flag and the exact downloaded manifest is not discarded with scratch files.
4. The restored application database contains `_PagneticRecoveryHold`; direct startup and SQLite→PostgreSQL transfer refuse it. Before any release decision, run `pnpm exec tsx scripts/replay-privacy-receipts.ts /absolute/NEW-database.sqlite /absolute/NEW-database.sqlite.verified-manifest.json` with writers stopped. It requires a complete, authenticated, two-pass-stable receipt inventory, retained receipt/recovery-key history, the verified restore manifest and exact tenant/order scope. Exact redaction requests are replayed through the existing erasure worker. Exact data-copy requests are reconstructed and collected to `EXPORT_READY_OWNER_DELIVERY`; a previously owner-confirmed request is accepted only after its signed request/scope/key/actor-bound delivery audit verifies, even when downloaded artifacts have expired and been purged. It is never recollected or given a new deadline. Missing/tampered delivery audits, corrupt/old receipts, inventory changes, absent historical keys, reinstall-generation conflicts, expired unfinished requests and over-limit scopes remain review-required or fail closed. No unrelated tenant/order is touched.
5. Existing backups may predate independent receipts. Treat that as an explicit backfill gate: reconcile the complete receipt inventory from the first deployment boundary and document the absence/coverage of earlier requests before release. A single sidecar/tombstone snapshot is not evidence that later receipts were applied.
6. Verify the recorded application release and schema. Run migration status/diff against the restored copy, compare merchant, experiment, assignment, financial ledger and audit counts to the backed-up evidence, and verify field decryption. Test interrupted job recovery and dedupe without remote side effects. Run suitable application health/readiness checks with the restored copy and isolated configuration; production-only endpoint checks need separately recorded live evidence. Review every unresolved privacy request and the retained aggregate/backup-erasure policy. Replay or collection output is not legal completion or delivery proof.
7. With the restore still isolated and all writers stopped, release the hold only through the shared audited service exposed by `scripts/release-recovery-hold.ts`: `pnpm exec tsx scripts/release-recovery-hold.ts /absolute/NEW-database.sqlite /absolute/NEW-database.sqlite.verified-manifest.json evidence-id operator-identity privacy-review-ref backup-review-ref legacy-inventory-ref receipt-quiescence-ref`. The five references must identify immutable operator-controlled evidence; placeholders are not approval. The service rechecks the signed READY hold, current receipt inventory, retained key fingerprints, restore manifest, application source, schema and protected-data fingerprint in one transaction, then appends a signed audit and changes the hold to signed RELEASED atomically. Stale, future, changed, missing-key, malformed, unresolved, duplicate or concurrent release attempts fail closed. A RELEASED string alone is never trusted: startup and SQLite→PostgreSQL transfer verify the hold, replay evidence and release audit signatures and bindings.
8. For actual recovery only, stop all old writers first, preserve the old database/WAL and incident evidence, deploy the matching release, point `DATABASE_URL` at the verified released database, and start exactly one writer with storefront serving disabled. Resolve pending leases safely, reconcile Shopify financial events and verify health before lifting the kill switch. No automated script performs this operational cutover, serving change or customer communication.
9. Record incident start, snapshot age, download/decrypt/DB validation time, receipt inventory/replay result, hold-release evidence, full application recovery time, counts, release/schema identity, operator and remaining anomalies. Approve reopening only when the full ≤4-hour target, data checks, privacy review and explicit hold-release authority pass. Dispose of the explicitly identified drill copy using the approved retention procedure.

## Local evidence and limitations

`tests/sqlite-backup.test.ts`, `tests/privacy-recovery-integration.test.ts` and `tests/recovery-reopening.test.ts` use real SQLite files and an isolated in-memory object adapter. They cover encrypted row roundtrip, live WAL inclusion, wrong-key/tamper rejection, corrupt upload/readback, stale proof, refusal to overwrite, restore quarantine, receipt replay, data-copy reconstruction, bounded database identity, signed audited release, concurrent single-winner release, rollback and a second recovery cycle. The PostgreSQL rehearsal also proves held-transfer refusal and authenticated released-transfer acceptance. Passing these tests does not prove S3 permissions, real networking, host-volume encryption, offsite key availability, provider retention, alert delivery, legal review or full application recovery in the intended environment. See [47-audited-recovery-reopening-and-delivery.md](./47-audited-recovery-reopening-and-delivery.md).
