## Workflow

1. Authenticated privacy intake stores the exact canonical order scope encrypted, with independent lookup and storage key fingerprints. No customer contact address is invented or retained from the webhook.
2. `/internal/privacy` is an automation-secret-authenticated POST, independent of merchant maintenance and Shopify offline sessions. Production supervision calls it every five minutes. Uninstall does not prevent collection or deadline escalation.
3. A run purges at most100 expired chunks and escalates at most100 overdue requests. It validates retained key coverage even when nothing is queued. It attempts at most20 collection steps and stops starting steps after30 seconds. Each collection transaction has a30-second timeout; the HTTP supervisor deadline is90 seconds and ambiguous timeout terminates its own application group before another run.
4. A step acquires the common runtime lock, then exact request authority. It collects one authorized order, creates an authenticated encrypted chunk and advances progress in the same transaction. Pre/post lease checks prevent a superseded or expired worker from committing. Successful progress resets consecutive failure attempts; a10000-order request is not limited to ten successful chunks.
5. All chunks must exist, have contiguous ordinals and remain unexpired for downloads to be available. The request enters `EXPORT_READY_OWNER_DELIVERY`; `completedAt` remains null and `deliveryConfirmed` remains false.
6. Manifest, download and confirmation always verify the current Shopify account owner through an online token exchange tied to the authenticated session-token subject. During the same install generation, the app also requires its persisted `OWNER` role. A request captured before uninstall can be recovered after a genuine reinstall without recreating that role only when its encrypted v2 scope contains a different authenticated installation-generation hash. Staff/collaborator status, same-generation no-role access, mismatched identity, expiry or provider failure deny access. Returned access tokens and associated names/email are discarded; no new online session is persisted.
7. Each successful download records an access-only audit entry. Parts are attachments with no-store/nosniff headers. After the same verified owner has downloaded every current unexpired part, they may explicitly attest that they securely delivered the copy and provide a bounded immutable evidence reference. One signed tenant-independent delivery audit is appended and the request moves to `OWNER_CONFIRMED_SECURE_DELIVERY`; replay, missing parts, another actor, artifact expiry and audit tampering fail closed. The evidence reference is stored as an HMAC digest, not plaintext. This confirms only the owner's explicit active-copy delivery action: `backupErasureVerified` remains false and `legalReviewRequired` remains true. No email or recipient identity is invented.
8. Chunks expire at the earlier of seven days after collection or the request deadline. Expiry cleanup marks unresolved requests for review before deleting expired chunks. Purging does not assert that historical backups or owner-downloaded copies were erased.

Pending redactions, owner-ready copies and persistent review statuses keep the worker attention state non-green/HTTP207; a previous deadline alert cannot disappear merely because it was already escalated. Responses expose aggregate counts/flags only, never request/order/shop identifiers, ciphertext, hashes or errors containing provider data.

## Export scope and limits

The collector covers exact tenant/order-scoped legacy orders/refunds/attribution, v2 ledger/lines/refunds/attribution, sanitized immutable financial revisions and directly linked measurement records. Queries page at500 rows and ID batches at100. It does not follow a shared assignment into other orders. Unknown signed capabilities are not decoded as authority; canonical financial payloads are strictly allowlisted. Shared visitor-outcome aggregate values that may contain unrelated orders/sessions are explicitly omitted.

The collector accounts each source row before adding it to retained arrays: at most2000 source rows and4 MiB per call, with a1 MiB canonical payload limit before parsing. The encrypted artifact's pre-encryption envelope is capped at5 MiB. Limits fail closed to `REVIEW_REQUIRED_EXPORT`; no truncated success is returned and these failures do not burn repeated retries. Query pagination is not a proof of production memory capacity; unusually large source rows and an offline/streamed path for over-limit requests still need operational handling. A successful active-data copy does not prove that ambiguous identity joins or retained backup data were fully searched.

## Redaction and recovery journal

Customer redaction now progresses through suppression, bounded exact graph discovery, financial/operational deletion, identity tombstones, analysis invalidation and verification. It records encrypted graph evidence and retains the terminal `ACTIVE_DATA_ERASED_BACKUP_REVIEW` state until backup/journal deletion is independently verified. Shared identities that would cross tenant or unauthorized order scope fail closed; a stale lease cannot commit any phase.

SQLite backup creation now emits an optional encrypted `.privacy.enc` sidecar containing only keyed suppression digests. The sidecar is uploaded/read back with the database artifact, authenticated by the independent backup key, included in retention checks, and re-applied idempotently before a restored database is copied into service. It contains no plaintext hashes in object names or manifests. Restore remains quarantined while complete signed receipt replay reconstructs redaction and data-copy work. Data-copy receipts are collected again to owner-ready state, never falsely marked delivered. Audited technical reopening is a separate signed transaction; it is not an application start, serving change, backup-erasure finding or legal completion. This is tested locally but still requires a real off-volume bucket, independent escrow, restore drill and legal/operational review.
